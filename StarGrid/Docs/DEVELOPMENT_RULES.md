# StarGrid 开发规范 / v1

## 最高原则

StarGrid 按长期持续更新产品开发。Demo 20 关、首发 50 关，但架构必须支持
200、500+ 关以及继续扩展。

## Codex 强制文档同步

Codex
每一次修改代码、数据、玩法、规则、存档、页面或测试，都必须在同一次任务中更新相关文档。没有更新文档的功能修改，视为任务未完成。

每次至少检查： - GAME_DESIGN.md - Docs/LEVEL_DESIGN.md -
Docs/RULE_SYSTEM.md - Docs/UNITY_ARCHITECTURE.md - Docs/TEST_REPORT.md -
CODEX_TASK.md - README.md - Docs/CHANGELOG.md

只更新真正受影响的文档，但必须主动检查。

## 每次任务完成流程

1.  读取现有设计和规范。
2.  修改代码/数据。
3.  运行自动测试。
4.  完成必要手动验证。
5.  更新相关设计文档。
6.  更新 TEST_REPORT.md，明确已验证/未验证。
7.  更新 CHANGELOG.md。
8.  更新 CODEX_TASK.md 当前状态。
9.  最后才能认为任务完成。

## 禁止事项

-   禁止写死总关卡数。
-   禁止把 20、50、100、200、500 当代码上限。
-   禁止用预存 solution 与玩家棋盘逐格比较作为通关条件。
-   禁止默认所有关卡必须唯一解。
-   禁止新规则绕过统一 RuleSystem。
-   禁止为了 Demo 制作无法扩展的临时代码。
-   禁止静默破坏旧存档。
-   禁止修改玩法后不调整测试。
-   禁止文档与实际代码不一致。

## 架构原则

-   LevelData 数据驱动。
-   RuleSystem 模块化。
-   Solver 与 UI 分离。
-   BoardState 与表现层分离。
-   导航从关卡数据派生。
-   SaveData 使用稳定 level id。
-   新机制优先通过字段/规则模块扩展，避免 level-id 特判。

## 新机制准入

规则定义 → 数据契约 → solver/validator 支持 → 自动测试 → 教学方式 →
样板关 → 真人试玩 → 批量使用。

## 长期规模检查

每次新增系统都要问： 1. 500 关时是否仍可维护？ 2. 新增第 501
关是否主要只需数据？ 3. 新规则是否可模块化扩展？ 4. 存档是否按稳定 id
工作？ 5. 关卡选择是否支持章节/分页/地图？ 6. solver
是否明确能力范围和失败策略？ 7. 文档和测试是否同步？

## Git 提交

一次提交保持主题明确。提交前确保测试结果、代码和文档处于同一版本。重要玩法/架构决策写入
CHANGELOG，避免只存在聊天记录。
