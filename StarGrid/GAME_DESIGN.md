# StarGrid · 星星方格 / 长期产品设计 v3

## 产品定位

竖屏、单人、简单干净的规则解谜游戏。核心体验是"读懂少量规则 →
在棋盘中放置星星 → 即时验证 →
获得通关反馈"。低美术成本、强规则扩展，适合长期持续增加关卡。

当前阶段继续使用 WebDemo 验证玩法，不创建 Unity 正式项目。Demo 先做到 20
关；正式首发目标 50 关；长期内容系统按 200、500+
乃至持续扩展设计。任何底层实现都不得把 20、50、100、200 或 500
写死为上限。

## 长期内容战略

长期关卡通过以下维度组合产生： 1. 棋盘尺寸变化。 2.
每行、每列、每区域星数配额变化（starQuota，为未来 2★ 等玩法预留）。 3.
启用规则及规则组合变化。 4.
区域形状、固定星、禁止格、局部目标等参数变化。 5.
新机制与旧机制重新组合。

新增机制遵循"教学 → 练习 → 组合 → 考验 →
Boss"。不能仅靠放大棋盘或提高试错量制造数百关。

## 阶段规划

-   Demo：1--20 关，验证教学、核心规则、移动端体验和难度曲线。
-   正式首发：1--50 关，形成完整首发内容。
-   第一轮扩展：51--100 关，加入更多成熟规则组合。
-   长期：101--200、201--500+，按章节持续扩展，不设代码上限。

建议每 10--20 关形成小主题，每 20--50
关形成大章节。后期优先使用成熟机制组合产生深度，不要求不断增加新规则。

## 胜利与解

不强制唯一解。玩家当前棋盘满足该关所有启用规则即胜利，不得与预存答案逐格比较。

关卡可以标记 multi、limited、unique，但 solutionType
是分析信息，不是统一胜利条件。唯一解适合高难、Boss
或特定每日挑战，但不是硬性要求。难度不能只按解数量判断。

## Demo 1--20 关

-   第 1 关：2×2，共 4 格，首次教学。
-   2--3：3×3 → 4×4，学习行列。
-   4--7：4×4 为主，引入"不接触"。
-   8--12：4×4 → 5×5，引入颜色区域。
-   13--16：5×5 → 6×6，完整基础规则。
-   17--19：6×6，提高区域与组合推理。
-   第 20 关：第一章
    Boss，明显更难，但必须有解，不靠无解或纯试错制造困难。

## 长期机制池

以下机制提前规划，但不代表一次全部开发： - 2★ / 多星配额。 - 固定星
givens。 - 禁止格 blockedCells。 - 不同区域不同星数配额。 -
部分区域参与规则。 - 至少/至多 N 星的局部限制。 - 特殊区域关系。 -
星座/图形附加目标。 - 其他低美术成本、可通过规则表达的机制。

每个机制正式进入批量关卡前必须经过原型、solver/validator
支持、自动测试、教学设计和真人试玩。

## 每日挑战

每日挑战采用连续两关： 1. 每日第一关：极简单热身，小棋盘，快速完成。 2.
每日第二关：真正高难挑战，使用当前已经教学过的成熟规则。

第二关不强制唯一解，只要求有解、规则合法并达到目标难度。唯一解可作为分析标签。

## 难度

唯一解不等于困难，多解不等于简单。未来 Difficulty Analyzer
应综合棋盘尺寸、星数、区域复杂度、解数量、明显落点、强制步骤、推理链长度、跨区域推理和规则组合。

Solver
长期不仅负责找答案，还要承担合法性验证、解数量分析、关卡生成辅助和难度分析。

## 数据与架构

LevelData 至少规划：
id、chapter、levelNumber、size、name、kind、rules、regions、starQuota、givens、blockedCells、difficulty、tutorial、solutionType、tags、version。

字段可渐进实现，但模块边界不得阻止后续扩展。

Solver/RuleSystem 必须逐步从当前固定 6×6、1★能力升级为
size/rules/starQuota 驱动。Demo
只实现实际需要的能力，但禁止写死会导致后续大规模返工的假设。

## 长期原则

1.  低学习门槛，高组合深度。
2.  新鲜感来自规则组合，而不是单纯增大棋盘。
3.  所有关卡必须可验证、有解；唯一解按设计需要选择。
4.  关卡数据化，代码不感知固定关卡总数。
5.  新机制必须可教学、可测试、可组合。
6.  WebDemo 先验证体验，再进入 Unity。
7.  任何代码变化必须同步维护文档和测试，详见 Docs/DEVELOPMENT_RULES.md。
